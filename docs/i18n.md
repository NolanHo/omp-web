# Internationalization

omp-web's interface uses a small internal i18n layer. It is intentionally kept
inside the application instead of introducing another runtime dependency, so
the UI can support more languages without coupling the server, API responses,
or omp's own output to a particular language.

## Current Languages

The built-in language packages are:

- `en` - English
- `zh-CN` - Simplified Chinese

The initial locale is inferred from the browser. Users can change the locale
from the language control in the top bar. The selected locale is persisted in
`localStorage` under `pi-locale` (the key predates the rename and is kept for compatibility).

## Using Translations In A Component

Client components should get the translation function from `useI18n`:

```tsx
import { useI18n } from "@/hooks/useI18n";

export function ExampleButton() {
  const { t } = useI18n();

  return <button aria-label={t("example.open")}>{t("example.open")}</button>;
}
```

The component must be rendered below `I18nProvider`. The application root
already provides it in `app/page.tsx`.

Use parameters for values that change at runtime instead of concatenating
translated fragments:

```tsx
<span>{t("session.messageCount", { count: messageCount })}</span>
```

The corresponding message can use `{count}`:

```ts
"session.messageCount": "{count} messages"
```

This keeps the sentence structure under the control of each language package.

## Adding A New Language

### 1. Create The Message File

Add a file under `lib/i18n/messages/`, using a BCP 47-style identifier. For
example, a Japanese package would be `lib/i18n/messages/ja.ts`:

```ts
import type { LocalePlugin } from "../types";

/** omp-web Japanese language package. */
export const jaLocale: LocalePlugin = {
  id: "ja",
  label: "日本語",
  messages: {
    "common.language": "言語",
    // Add the rest of the shared keys here.
  },
};
```

The message keys must remain stable and language-neutral. Copy the complete
key set from `lib/i18n/messages/en.ts` when starting a new package. Missing
keys fall back to English, but a complete package is preferred for a user
facing language.

### 2. Register The Package

Import and register the package in `lib/i18n/registry.ts`:

```ts
import { jaLocale } from "./messages/ja";

registerLocale(jaLocale);
```

`LocalePlugin.id` must be unique and non-empty. The label is displayed in the
language selector. `getSupportedLocales()` automatically exposes registered
packages to the UI.

### 3. Update Locale-Specific Types If Needed

The built-in `Locale` type currently lists `en` and `zh-CN` for compile-time
safety. When adding a built-in language, update that union in
`lib/i18n/types.ts` and update any locale validation that intentionally lists
the built-in identifiers.

### 4. Add Tests

Extend `lib/i18n/registry.test.mjs` when browser-language detection or registry
behavior changes. Extend `lib/i18n/format.test.mjs` when interpolation or
locale-aware formatting changes. A new language should at minimum verify its
registry id and a representative translation.

## Adding Or Changing UI Text

1. Add a stable key to both `lib/i18n/messages/en.ts` and
   `lib/i18n/messages/zh-CN.ts`.
2. Put keys under a feature namespace such as `chat.*`, `files.*`,
   `settings.*`, or `common.*`.
3. Use `t("namespace.key")` in visible text, `title`, `aria-label`, and
   `placeholder` values.
4. Use interpolation for counts, names, paths, and other runtime values.
5. Keep product names, model names, provider names, commands, file paths,
   user content, tool output, and server-provided error details unchanged.
6. Do not translate an API error by matching its English text. Translate only
   the local UI fallback around it.

Keep established technical terms in English when translating them would make
the interface harder to map back to commands, configuration fields, or omp
documentation. This includes terms such as `Agent`, `API Key`, `Provider`,
`Token`, `Shell`, `Git`, `HEAD`, `OAuth`, `MCP`, and `Mermaid`; preserve their
conventional casing. Translate the surrounding actions and status text. Common
concepts with clear localized forms — model, plugin, skill, prompt, context,
cache, worktree, diff — stay localized; their renderings are fixed by the
glossary below so the same concept never appears under two names.

For example:

```ts
// en.ts
"files.uploadedCount": "{count} uploaded"

// zh-CN.ts
"files.uploadedCount": "已上传 {count} 个文件"
```

```tsx
<span>{t("files.uploadedCount", { count: uploadedCount })}</span>
```

If a key is missing from the selected language, the formatter first tries the
English package and finally returns the key itself. Missing keys also produce
a development warning, which makes incomplete translations visible during
development.

### Punctuation and spacing

- Full-width punctuation in Chinese sentences: `，。：；！？（）——“”`.
- Ellipsis is a single `…`, never `...`.
- Put one space between a number and the following Chinese noun: `3 个文件`,
  `128 行`.
- Keep half-width punctuation inside code, paths, commands and identifiers.

### Counts and plurals

The formatter has no plural rules. When the English sentence inflects, choose at
the call site (`count === 1 ? t("models.providerModelCountOne") : t("models.providerModelCount")`).
Chinese variants usually carry the identical string; the pair exists for
English.

The preferred shape is a `<key>One` sibling plus the base key. Three older
pairs predate it and are left alone: `plugins.diagnosticsCountOne` /
`diagnosticsCountMany`, `chat.todoTask` / `todoTasks`, and `chat.match` /
`matches`. Do not introduce a fourth shape; convert an old pair only when you
are already editing that surface.

### What stays English

Product names, model names, provider ids, paths, commands, environment
variables, HTTP headers, protocol names, role ids and tags, git status codes,
time/size units in compact badges, and anything the agent, a provider, or an
API returns verbatim. Translate the local shell around such values, not the
value itself.

### Known boundaries

- **Settings schema.** `/api/settings` serves omp's own settings definitions:
  tab and group labels are localized through `settings.tab.*` /
  `settings.group.*` maps, but the 378 field labels, descriptions and option
  names stay English. They are config-schema documentation and mapping 1:1 to
  `config.yml` fields is the point.
- **Server errors.** The web-access API answers with a stable `code` alongside
  the original English `error`; the UI maps `access.error.<code>` and falls
  back to the raw `error` for unknown codes. The UI never matches on English
  text. The one place that classifies English is the route layer, which reads
  the fixed strings `bin/web-auth-store.js` returns from its shared password
  validator; an unclassified message returns no code, so the raw `error` wins.
- **Role names.** Built-in model roles are localized through
  `translateRoleName()` (`lib/i18n/role-names.ts`); roles added in
  `modelRoles` keep the label the agent sends.
- **Notices.** `useAgentSession` translates notices when it emits them, so a
  notice already on screen keeps the language it was created in; new notices
  follow the current locale.
- **Timestamps.** Dates and times follow the interface locale, not the
  operating system locale.
- **Inline errors.** When a block fails mid-render, the visible line is a
  localized headline (for example `i18n.thinkingUnavailable`) and the raw error
  text moves to the `title` attribute, so technical detail stays inspectable
  without leaking English prose into the Chinese interface.
- **Document metadata.** `app/layout.tsx` metadata and the web manifest keep
  the English product name `omp-web`.

## Design Principles

omp-web is a user-facing web interface. Internationalization is therefore an
accessibility and usability feature: people should be able to understand and
operate the interface in a language they are comfortable with. Language
support should lower the barrier to using omp-web, not be treated as a measure
of technical expertise or as a reason to exclude otherwise useful
contributions.

The i18n layer is deliberately incremental. Contributors can add a language
or improve a small group of UI messages without rewriting API contracts,
changing omp's output, or introducing a large translation framework.
